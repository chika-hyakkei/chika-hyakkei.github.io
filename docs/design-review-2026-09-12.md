## 優先修正

### A01 / P1: 侍・錬金術師のランキングが拒否され、再送待ちも詰まる

根拠: `ranking-api/src/index.ts:6,16`、`app/ranking.ts:76`、`app/page.tsx:325`。

ゲームには8職業あるが、APIの許可リストは6職業。正常な終了記録で職業だけを変更すると、戦士は200、侍と錬金術師は400になった。さらに `flushPendingRankings` は最初の例外でループを止めるため、先頭に侍、その次に正常な戦士の記録を置くと「送信0件・保留2件」になる。画面は形式不正でも通信不良と表示する。

推奨: 職業IDをクライアント/API共通の定義へ寄せ、APIを先に8職業対応させる。再送では一時的な通信失敗と恒久的な形式不正を区別し、不正な1件が後続を止めないようにする。記録を黙って削除せず、失敗理由を保持する。

合格条件: 全8職業×全4終了理由を実際のWorker検証関数に通す。形式不正→正常、通信断→復旧、同一ID再送の組合せも確認する。

### A02 / P1: 宝箱の装備抽選で武器・防具が出ない

根拠: `app/page.tsx:327`、`app/items.ts:82`、`app/page.tsx:364`。

宝箱の種類判定に使った乱数 `r` を、そのまま装備一覧の添字にも使っている。装備の分岐に来る時点で `r >= 0.76` なので、武器→防具→装飾品の順の一覧の末尾だけが選ばれる。

1・21・41・61・81階で各10万シードを実行したところ、それぞれ装備24,130件の内訳は「武器0・防具0・装飾品24,130」。また、現行の3〜99階の全商店を列挙すると、武器・防具60件のうち登場するのは50件だけだった。新規通常プレイでは残り10件を宝箱から補うこともできない。

推奨: 宝箱の種類決定と、中身の選択で別々に乱数を進める。アイテムIDごとの到達可能性を検査し、100件の「存在」だけでなく「入手可能」を確認する。

合格条件: 各階層帯で武器・防具・装飾品が出現する。全通常入手対象IDに入手経路がある。分布変更後は回復・金貨の配分も再計測する。

### A03 / P1: 壊れたセーブを正常と判定し、復旧に失敗する

根拠: `app/page.tsx:65,66,247,267,387`、`app/storage.ts:13,24`。

Runの検査は地図寸法など一部に限られ、描画で必須の `seen`、敵配列、主要数値、戦闘フェーズとbattleの整合などを十分に確認していない。正常なバックアップがあっても、`seen` を欠いた現在Runを「current」として採用し、描画相当の参照で例外になった。

Metaでも `bestScore:null` が補完されず採用され、タイトルの数値表示で例外になる。復旧画面の操作はRunだけを対象とするため、このMeta異常には対処できない。`saveRecoverable` も、書き込む新しい値をnormalizerで検査しておらず、直前値の検査だけを行っている。これは保存仕様の「保存前に構造検査」と一致しない。

推奨: Run/Metaの実際の正規化関数を保存モジュールから検証できる形へ分離する。旧データの補完と、不正データの拒否を明示する。Metaのバックアップ復元も復旧UIから選べるようにし、保存容量不足などの失敗も通知する。

合格条件: 必須項目欠損、null/不正数値、寸法不正、battle不整合、破損JSON、容量不足に対し、正常値の保持・隔離・バックアップ復旧を確認する。既存の正常な旧セーブは失わない。

### A04 / P1・検証設計: 現在の48,000走は実ゲームの難易度を検証していない

根拠: `scripts/balance-simulator.mjs:1,23,112,128`、`tests/balance.test.mjs:13`、ADR-014。

シミュレーターは実戦の敵、装備、技、ダメージ計算を呼ばず、独自のHPと危険率を使う。死因も一部は状態異常やMPの実際の因果関係ではなく、乱数から分類されている。実ゲームの敵攻撃力や魔法反射処理を変えても、その変更だけではこの結果は変わらない。

ADRに独立した抽象モデルであることは明記されている。しかし、その値を根拠に「全職業の難易度が目標帯内」「現在の調整を崩していない」と判断することはできない。3.85%・13.21%はこのモデルの出力であり、現行ゲームの到達率としては未検証と扱うべきである。

推奨: Reactから純粋な戦闘・報酬・探索処理を段階的に分離し、ゲームとシミュレーターが同じ関数・マスターを呼ぶ方式へ移す。行動を選ぶAIだけを初見/予告活用などに分ける。既存モデルは仮説用として区別する。

合格条件: 本体の攻撃力・回復率・装備効果を変えると、対応する実戦シミュレーション結果も変わる。魔法反射・MP吸収・再生の職業別影響を実際のダメージと資源消費から説明できる。

## ゲーム進行・記録・操作の不整合

### A05 / P2: 遺物の3択が同じ品になる

根拠: `app/page.tsx:202,405`、`app/items.ts:62`。

候補を `offset * 7 % pool.length` で選ぶため、遺物を3個取得した時の残り7個では全候補が同じ添字になる。通常の40階報酬相当で、実行結果は同じ遺物3個になった。残り2個でも重複する。

加えて `r10` の百景の鍵は「100階の扉を開いた証」だが、序盤から通常の報酬候補に含まれ、戦闘上の効果がない。強化報酬として選ぶ価値が分かりにくい。

推奨: 重複なしの抽選にし、候補が3個未満なら実数だけ表示する。踏破記念品は最終ボス報酬へ分けるか、通常遺物としての効果を定義する。

### A06 / P2: 宝箱依頼の達成が次階で取り消される

根拠: `app/page.tsx:199,322,327`。

依頼進行に、現在階で開いた座標一覧 `opened.length` を使っている。この一覧は新しい階で空になるため、3/3達成済みのRunを階移動させると0/3・未達成になる。

推奨: 現在階の開封座標と、冒険全体の累計開封数を分ける。達成状態は以後の階移動で後退させない。旧Runには現在階の開封数を下限として補完し、過去の未記録分を推測で捏造しない。

### A07 / P2: テストモードが通常の恒久記録を変更する

根拠: `app/page.tsx:300,301,323,355`、ADR-021。

終了処理ではランキングと匿名テスト記録だけが除外され、Metaの最高階・最高得点・討伐数・熟練度・踏破フラグを通常どおり更新する。テストで100階踏破を渡すと、`bestFloor=100, cleared=true, mastery.warrior=10` になった。図鑑の入手・討伐記録にもテスト除外がない。

深層職をテストで解放すること自体は既存ADRで許容されているが、それと通常の最高記録まで更新することは別である。旧Metaの安全地点補完も `bestFloor` を使うため、以前のテスト記録を通常到達と誤認する余地がある。

推奨: 通常MetaとテストMetaを分けるか、通常Metaへ反映する項目を明示的に限定する。すでに混ざった記録は識別できないので、勝手に削除せず移行方針を相談する。

### A08 / P2・調整上の懸念: 奈落降下の深層開始能力が不足しうる

根拠: `app/descent.ts:37,38`、`app/page.tsx:95,190,318,344`。

着地レベルは階数の半分、上限45。貸与品には商店の深層強化補正がない。実際の着地生成と敵処理を使うと、91階の戦士はHP262・攻撃105・守備57。出現可能な深骨ネズミはHP794・攻撃300で、初手の強攻撃を通常防御してもHP87まで減った。無防御ならHP0になった。

これは全遭遇が突破不能という意味ではないが、「再挑戦を短くするルート」の開始状態として再検証が必要である。降下ミニゲームの時間・障害物数も11階と91階で共通なので、着地後の能力をミニゲームの難しさだけで正当化できない。

推奨: 各安全地点の通常プレイ到達時のレベル・装備・資源分布を実戦で測り、その下側の妥当な水準から貸与値を決める。全職業で着地後の通常敵1〜2戦を評価し、到達短縮として機能するか確認する。

### A09 / P2: 到達回数が二重計上され、降下ルートも混ざる

根拠: `app/telemetry.ts:14,15,16`、`app/page.tsx:318,322,323`。

階到達時に加算し、終了時にも `recordFloor` を呼ぶ。同じ1走で10階へ到達して死亡すると10階到達数は2になる。1階死亡も同様で、この値を到達率の分子にできない。

降下ルートでも `recordRunStart` が1階開始を記録し、経路や開始階を保持しない。通常プレイの到達率と深層からの再開を後から分離できない。

推奨: `runId`、`route`、`startFloor` と、冒険ごとの到達済み階を記録する。同一Run内の到達は一度だけ数える。旧集計は訪問イベント数として区別して保持する。

### A10 / P2: キーボード入力が戦闘演出の終了待ちをすり抜ける

根拠: `app/page.tsx:280,354,356,363`、`app/grim.css:24`。

表示上の手番は1,350msまで続くが、内部の敵処理待ちは約650msで解除される。マウスはCSSの `pointer-events:none` で止まる一方、キー操作の受付は `turnStep` を確認しない。敵演出中・pendingなしの状態で攻撃を渡すと、次の攻撃と敵処理待ちが受理された。

推奨: 入力可否をマウス・キーボード共通の状態判定に集約する。手番のタイマーをまとめ、次戦闘や終了後に古いタイマーが状態を書き換えないようにする。図鑑などの前面画面を開いている時のキー受付も同じ方針で扱う。

### A11 / P2: 初回訪問直後のオフライン起動を保証できない

根拠: `public/sw.js:2,7,38`、`app/page.tsx:263`。

インストール時のキャッシュ対象はHTML2件、manifest、faviconだけで、ゲームを起動するJS/CSSは含まれない。それらはService Workerの管理が始まる前に初回ページで読み込まれうる。install処理だけを実行したメモリー内診断でも、次のオフラインJS取得は失敗した。

推奨: ビルドで起動に必要なアセット一覧を生成し、HTMLと対応するJS/CSSを揃えてキャッシュする。初回訪問→通信断→再起動、旧版→更新→通信断を実機で確認する。キャッシュ書き込みの完了もイベント寿命に含める。

### A12 / P2: 遺品なしで再死亡すると古い墓が残る

根拠: `app/page.tsx:323,406`。

死亡時に新しい装備が1個以上ある時だけ墓を置き換える。40階の墓がある状態で、遺品なしで1階死亡させると40階の墓が残った。「再死亡で前の墓を置き換える」という基本方針と異なる。貸与品しか持たない降下Runでも発生する。

推奨: 通常死亡ごとに墓を置き換える。新しい遺品がなければ空墓または墓なしとするか、意図的な救済仕様として決定・明記する。回収時に持ち物8枠を超えられる点も、満杯時処理と併せて決める。

### A13 / P2: 100位より下の今回記録を表示できない

根拠: `ranking-api/src/index.ts:31,34`、`app/page.tsx:325,415`。

APIが返すのは上位100件だけで、highlightはその100件内を強調するだけ。新しい記録が101位以下なら返却されないのに、画面は「今回の記録を点滅表示しています」と案内する。

推奨: 上位一覧とは別に今回の記録・実際の順位を返し、順位外でも結果画面に固定表示する。

### A14 / P2: 英語版では行動結果や通信失敗の具体的な内容が失われる

根拠: `app/page.tsx:296,403,415`。

戦闘、探索、商店のメッセージが、実際の結果によらない固定文へ置き換わる。英語版では入手した品名、与えた傷、反射の結果、購入失敗の理由などを日本語版と同じ情報量で読めない。ランキング状態も一律の更新通知になる。

推奨: 結果を `{type, itemId, amount, reason}` のような安定したイベントとして持ち、日英の表示文をそこから作る。現在の固定文方式は文書で制約として認識されているが、「英語だけで主要結果を理解できる」という完了条件は未達と扱う。

### A15 / P3・仕様差分: 25素体という資料と、実際の描画が一致していない

根拠: `app/page.tsx:206,395,402`、`app/grim.css:9`。

描画の素体番号は `%10` で丸めており、用意されている基本シルエットは10系統。25種類の戦術データと25種類の見た目は別である。また、100通常個体とは別に階層主がおり、最初の「ボスを含む100体」仕様とも一致していない。後者は既存todoにも記録済み。

推奨: 見た目と攻略の対応を素体IDで固定する。図鑑再編は既存IDの移行方針を決めてから行い、数字合わせだけの削除・置換を避ける。

## 構造面の改善案

1. **処理と表示の境界**: `page.tsx` は約132KBで、戦闘、保存、終了、抽選、翻訳、演出が集中している。まず戦闘1ターン、宝箱、終了処理を小さな純粋関数として分離する。Reactの状態更新関数内から別の状態更新・タイマー・音を起こす処理を減らし、決定済みイベントをUIが再生する形にする。
2. **共通IDとデータ契約**: 職業IDの二重定義を解消する。Run/Metaの型だけでなく、古いデータを補完し、不正な値を拒否する実行時の検証を共通化する。装備能力・効果説明・実戦計算も共通マスターを正とする方針を維持する。
3. **終了処理の一度だけ実行**: 開始時に安定したRun IDを付け、終了結果・Meta反映・ランキング待ちを同じ終了IDへ結び付ける。現在は終了、保存、キュー作成が別経路なので、再読込や再実行時の整合をテストする。
4. **テストの役割**: `rendered-html.test.mjs` の23件中22件は主にソース文字列の照合で、ゲーム操作を実行していない。既存テストは補助として残しつつ、今回の再現条件を入出力のテストへ置き換える。セーブテストも独自の簡略normalizerではなく本番normalizerを使う。
5. **公開前の検査**: 現在の公開ワークフローはビルドのみ。フロントとWorkerの型検査設定を分けて通し、テストとAPI契約検証も公開前に実行する。型宣言不足の解決はWorker実行環境に合わせ、型検査を丸ごと無効化しない。

## 推奨実施順

1. ランキング8職業・再送、宝箱抽選、セーブ検証を修正し、それぞれ今回の再現条件をテストへ追加する。
2. 遺物の重複、依頼累計、テストMeta、墓、手番入力、順位外表示を修正する。保存形式へ追加する値は旧データの補完を先に定義する。
3. 実ゲームと共通の戦闘・探索シミュレーターを作り、通常ルートと奈落降下を分けて全8職業・複数ビルドを再計測する。到達率、残HP/MP、残薬、死因は実際の状態から求める。
4. PWA更新/通信断と英語結果表示を整え、PC・iPhone・Androidで開始→戦闘→宝箱→商店→終了→再開を通して確認する。
5. 説明なしの外部テストへ進み、ロードマップの初見理解・再挑戦意向・理不尽死の合格条件を評価する。

この順序なら、プレイヤーに届く不具合を先に減らし、その後の数値調整を信頼できる計測に基づいて行える。今回のレビューだけを根拠に敵全体を一括で弱体化したり、既存Metaを消去したりしない。
